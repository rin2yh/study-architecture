# README 規約

README は**入り口**として読む人向けの文書に限る。置いてよいのは次の 3 つだけ。

1. **概要** — その単位（リポジトリ / パッケージ）が何であるかを数行で
2. **環境構築・使い方** — 動かすために必要な前提と最小のコマンド
3. **詳細ドキュメントへのリンク** — 上に収まらないものの行き先

設計判断・構成の説明・ドメインの振る舞い・ディレクトリ構成といった**変わりやすい詳細は README に
書かず `doc/` 配下へ置き、README からはリンクだけ張る**。設計判断そのものは ADR（[[adr.md]]）が
単一情報源なので、README にも `doc/` の解説にも要約を写さず参照で張る。

- 例外: ADR 一覧（`doc/adr/README.md`）のような、索引そのものが目的の README
- パッケージの README は「そのパッケージの使い方」まで。層構成や設計方針は `doc/` 側に置く

理由: README は最も読まれる代わりに最も陳腐化する。実装が変わるたびに手が入る記述を入り口に
集めると、読み手は長い文書を読まされ、書き手は更新漏れを見落とす（実際に README のサービス数・
ポート・フレームワーク名・生成物のパスがまとめて実装から取り残された）。変わりやすい記述を
`doc/` へ寄せておけば、入り口は安定し、実装変更時に直すべき面積も特定しやすい。

## 値の一覧を README や doc に転記しない

ポート・サービス名・環境変数のような設定ファイルから読める値は、表にして写さず**単一情報源
（`compose.yaml` / `mise.toml` など）を参照させる**。

- ✗ ホストポートとコンテナ内ポートの一覧表を README に持つ（`compose.yaml` と二重管理になる）
- ✓ 「ホストポートは `compose.yaml` の `ports:` を参照」と書く

理由: 転記した表は更新されないまま残り、実装と食い違ったときにどちらが正しいか読み手に判断できない。
