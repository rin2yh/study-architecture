# ADR-202608150859: ドキュメント鮮度を AI の自動 draft PR で維持する

- Status: Accepted
- Date: 2026-08-15
- Relates to: ADR-[[202607020343]] (CI で構造を弾く枠。本 ADR は弾けないズレを直す枠), ADR-[[202606210900]] (意味判定を LLM へ委譲する先例), ADR-[[202606170901]] (生成で単一情報源に寄せる)

## Context

- ドキュメントの更新は人手の不定期棚卸しに依存しており、`README.md` / `doc/ops/**` は最終更新から
  実装側に 41〜49 コミット、`client/app/ui/README.md` は 101 コミットの差が開いていた。
- 実測した陳腐化: サービス表がコンテナ内ポート・inventory・ワーカーを取り違えたまま、フロントエンドの
  記述が Superseded 済みの TanStack Start のまま、実在しない ADR 参照が 2 件。
- 一方 `doc/adr/README.md` だけは追随できている。`.claude/rules/adr.md` が一覧更新を作業手順に
  埋め込んでいるためで、手順や機械に埋めた箇所しか保たれていない。
- ADR-[[202607020343]] の fitness function は「違反を弾く」枠であり、開いてしまった差を「直す」経路は無い。

## Decision

散文のズレを antigravity CLI (`agy`) に直させ、**結果は必ず draft PR にして人のレビューを挟む**。

- **入力は直近 1 週間の実装変更に絞り**、関係するドキュメントだけを直させる。
  → 溜まったズレを均すのが目的で、1 週間ぶんならレビューできる差分量に収まる。
- **仕組みを増やさない**: プロンプト組み立ても PR 作成もワークフローに直接書き、専用スクリプト群は
  置かない (`agy` の導入と実行だけ composite action へ括り出す)。
  → 対象が 1 ワークフローしかないうちは、抽象の維持コストのほうが大きい。
- **このワークフローに検査を持たせない**: 実在しない ADR 参照のような機械判定は、`.dockerignore` や
  `.ts` など Markdown 以外にも出る。AI の書き込み範囲外なのでここでは直せず、置いても手が出ない。
  → 弾く仕組みは ADR-[[202607020343]] の枠で PR CI 側に足す (GitHub #144)。
- **AI の書き込み範囲を機械で縛る**: 書き換えてよいのは Markdown のドキュメントのみで、実装ファイルと
  `doc/adr/**` は禁止する。範囲外を触ったら job を落とす。設計判断は人が起こす。
- **成否を終了コードで判定しない**: headless の `agy` は承認を得られないツールを soft-deny して exit 0 で
  素通りするため、`git diff` を唯一の判定材料にする。
- **認証は `GEMINI_API_KEY` を GitHub Secrets に置く**。GCP プロジェクトを要する ADC / Workload
  Identity は、この規模の学習リポジトリには重いため採らない。
- **モデルを明示指定する**: `agy` の既定は Gemini 3.1 Pro だが、API キーの無料枠はこれを
  `limit: 0` で拒む (実測)。Flash を指定して無料枠の範囲で回す。
- **`agy` にシェル実行を許可する**: headless では承認プロンプトを出せず、リポジトリを読む
  コマンドが自動拒否されて何も書かずに終わる。読み取り系だけを列挙する記法は効かず、
  `command(*)` でしか通らなかった (実測)。ランナーに認証情報を置かない構成と、実行後の
  書き込み範囲検査を担保にして許可する。

## Consequences

- ドキュメントの陳腐化が溜まったままになる状態が終わる。
- 外部 AI サービスへの依存が CI の**書き込み**経路に入る。draft PR + 書き込みパス制限 + ADR 禁止で
  信頼境界を保つが、レビュー無しのマージは前提から外れる。
- `agy` の headless 認証は 2026-08-14 に入ったばかりで、CI 用の API キー認証を求める upstream issue も
  open のまま。
- **当面はどのレーンも `workflow_dispatch` 限定**で入れる。実測前に `schedule` / `pull_request` を
  足すと実行回数だけ増えるため。昇格は手動実行での実測後に別途行う (GitHub #144)。その間、
  乗り遅れはマージ後の手動実行で見つかる形になる。
- compose.yaml の写しになる記述 (サービス表) は README から落とした。生成して置き続けるより、
  ポートやネットワークは compose.yaml を直接見るほうが確実なため。
- 無料枠のレート制限が実運用の上限になる。1 回の実行でリポジトリを読み切るだけの呼び出しが要り、
  無料枠では 429 で落ちる場面がある。継続運用には課金の有効化が要る。

## Alternatives considered

- **決定的レーンだけにする**: 外部依存ゼロで確実だが、散文のズレ (フレームワーク名・処理の流れ) は
  誰かが気づくまで残る。今回の陳腐化の大半がそこにあり、放置すると同じ状態に戻る。
- **サービス表を compose.yaml から生成して README に差し込む**: 表は腐らなくなるが、生成・検査・
  マーカー差し替えの機構を抱えることになる。表自体が compose.yaml の写しなので、置かないほうが軽い。
- **全部を AI に投げる**: 実装は単純だが、決定的レーンで得られる差分の安定性を捨てることになる。
- **自動 PR を作らず issue で報告する**: 気づきは供給できるが直す動機が続かず形骸化する。
  ADR-[[202607020343]] が warn 運用を退けたのと同じ理由。
- **Claude Code Action を使う**: 公式 action があり導入は軽いが、CLI 選定は利用者の意向で決まる。
