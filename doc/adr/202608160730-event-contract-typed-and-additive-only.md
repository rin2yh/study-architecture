# ADR-202608160730: イベント payload は型付き契約 + 追加のみで守る (version 番号は持たない)

- Status: Accepted
- Date: 2026-08-16
- Relates to: ADR-[[202607020343]] (フィットネス関数の枠。本 ADR はその 2 本目), ADR-[[202608150835]] (ブローカをポートで隔離), ADR-[[202608150830]] (再配送上限で DLQ へ隔離), ADR-[[202606300600]] (outbox), ADR-[[202607011621]] (独立デプロイ性 = 主駆動特性), ADR-[[202607020324]] (ECST で payload が太る), GitHub #108

## Context

- payload は `map[string]any` のまま consumer へ流れ、consumer が key と型アサーションを手書きしていた。`values[k].(string)` の失敗側を捨てるため、欠落・型違いが**ゼロ値へ化ける**。
- 実測: 発行している 4 フィールドのうち consumer が読んでいたのは `event` と `orderId` だけで、`paymentId` / `amountCents` はどこからも参照が無く、契約として検証される箇所が無かった。
- 現行コードでの壊れ方は 3 通りに分かれる。**黙って壊れるのは 3 番目だけ**。
  1. フィールド追加 → key 読みなので無害
  2. `orderId` の削除・改名 → parse が error になり再配送上限で DLQ。気づけるが遅く、ログが "invalid orderId" で原因が producer の契約変更だと読み取れない
  3. 型・単位・意味の変更で parse は通る → consumer がそのまま誤処理
- producer と consumer は独立にデプロイされるため、非互換変更は必ず両者が食い違う時間帯を作る。
- ECST (ADR-[[202607020324]]) で payload が太ると読まれるフィールドが増え、3 番目のリスクが上がる。

## Decision

イベント payload に **version 番号を持たせない**。代わりに次の 2 つで非互換を**起こせなくする**。

1. **wire 契約を型で閉じる** — 各 wire 契約パッケージに `Values` の逆方向 `Parse` を置き、consumer から map アクセスを無くす。記録済みフィールドの欠落・型違いは error にして DLQ へ倒す (ADR-[[202608150830]])。
2. **追加のみ許す** — 発行済みフィールドの削除・型変更を禁止する。削除は「optional へ落とす PR」→「削除する PR」の 2 段階。型変更は別フィールドを optional で追加して移行する。

決め手: version は非互換を**検出**するだけで**防止**しない。version を上げても旧 consumer は新 payload を処理できず DLQ に積まれる (= 壊れている)。防いでいるのは段階を踏む運用の方なので、番号ではなくその段階を機械化する。

- **記録**: 発行中の全イベント種のフィールド名・型・optional を `server/internal/eventcontract/testdata/schema.json` に置く。導出元は `Values` を実際の送出経路 (JSON 化 → 復元) に通した後の payload だけにする。スキーマを別に手書きすると二重管理で記録が嘘をつき、プロセス内の Go 型のまま記録すると往復で化ける型 (float64 の整数値は int64、非整数は string) を見逃す。
- **強制**: ADR-[[202607020343]] の枠に乗せて hard fail させる。`go test` は記録とコードが一致していること (フィールド集合・型・記録の必須/任意と `Parse` の実挙動) を見る。`server/tools/eventcompat` は base の記録と PR の記録を比べる。後者が無いと 1 PR で optional 化と削除を同時にやれてしまい、2 段階が成立しない。
- **記録とコードのフィールド集合は常に一致させる** (廃止するなら両方から消す)。ずれを許すと、記録だけ残したまま発行をやめる 1 PR が通り、旧 consumer が必須として待っているフィールドが無言で消える。
- **イベント種名は業務事実を指す** — エンコーディングの都合で変えない。新しい種は事実そのものが変わったときだけ起こす。

## Consequences

- フィールドを消すのに 2 回のリリースが要る。急ぎの削除ができない代わりに、混在デプロイで壊れる経路が無くなる。
- 発行しているが誰も読まないフィールドを作れなくなる。`paymentId` / `amountCents` も `Parse` の必須になり、契約が実際に検証される代わりに producer は「とりあえず載せる」ができない。
- 新規フィールドは optional で入れる必要がある (旧 producer がまだ発行していない間に必須にすると DLQ 行き)。必須へ昇格してよいかは全 producer のデプロイ状況次第で、機械では判定できない。
- `eventcontract.Contracts()` への登録漏れは検査を素通りする。イベント種の追加は登録込みでレビューする。
- 混在デプロイ中に受け取った payload が「どの世代か」は実行時に観測できない。追加のみを守る限り世代の区別が要らない、という前提に乗っている。

## Alternatives considered

- **payload に version を載せ、非互換で major を上げる (GitHub #108 の原案)**: 破壊的変更を表現できるが検出止まりで、旧 consumer が処理できない事実は変わらない。番号の管理コストに対して得るものが「壊れたと分かる」ことだけ。
- **メッセージ属性 (SNS MessageAttributes) に version を載せる**: ブローカ側フィルタに使えるが、ブローカ非依存の messaging ポート (ADR-[[202608150835]]) に broker 固有概念が漏れ、outbox テーブルにも列が要る。
- **非互換のたびに新しいイベント種を起こす**: 既存 consumer が種別フィルタで自動的に無視するので追加実装は要らないが、イベント名が識別子と世代の二役を負い、業務事実と表現が混ざる。
- **Protobuf + buf breaking で IDL 化**: 互換ルールがフィールド番号という言語仕様で担保され、検出も既製品で済む。ツールチェーンと payload 形式の見直しが要るためイベント 2 種の現状には重い。必要になったら記録済みスキーマを .proto へ移す。
- **ルールだけ決めてレビューで守る**: ADR-[[202607011621]] の「機械で守る」に反し、人手依存で劣化する。
