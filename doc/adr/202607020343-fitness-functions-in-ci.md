# ADR-202607020343: アーキテクチャ特性を CI のフィットネス関数で守る (第一号は量子越え同期呼び出しの許可リスト)

- Status: Accepted
- Date: 2026-07-02
- Relates to: ADR-[[202607011621]] (「特性はフィットネス関数で守る」原則。本 ADR はその実装枠), ADR-[[202606231000]] (schema 所有を DB ロールで強制 = 既存の暗黙 fitness), ADR-[[202606210900]] (what コメント lint), ADR-[[202606220716]] (量子別 CI 分割), ADR-[[202606261100]] (RED/SLO アラート = 継続型), ADR-[[202606301100]] (order↛member の結合撤去), ADR-[[202607020305]] / ADR-[[202607020324]] (同期結合を減らした対象), GitHub #98 (親)

## Context

- 方向 ADR-[[202607011621]] は「特性はフィットネス関数で守る」と原則を置いたが、具体の機構が未定。
- 実は暗黙のフィットネス関数が既にある: schema 所有を DB ロールで強制 (ADR-[[202606231000]])、what コメント lint (ADR-[[202606210900]])、量子別 CI 分割 (ADR-[[202606220716]])、Grafana アラート (ADR-[[202606261100]])。名前と枠組みが無く、原則を新規適用する手段が定まっていない。
- タスク 2 (ADR-[[202607020305]]) / タスク 3 (ADR-[[202607020324]]) で前進フローの同期結合を減らしたが、これが後から無言で復活する (誰かが gateway を 1 本足す) のを防ぐ機械が無い。
- golangci-lint を使用しており、`depguard` で import 方向を機械強制できる。

## Decision

アーキテクチャ特性を守る **triggered 型フィットネス関数を CI に導入**し、違反は **hard fail** でマージをブロックする。第一号は **量子越え同期呼び出しの許可リスト強制**。

- **第一号**: サービスが他量子へ同期呼び出し (gateway / HTTP クライアント) を持てるのは、明示した許可リストにある組み合わせだけ。リスト外の新規同期依存を CI で落とす。→ 独立デプロイ性・可用性 (主駆動特性) を守り、サーガ / ECST で減らした同期結合の逆戻りを防ぐ。
- **メカニズム**: golangci-lint の `depguard` 等で import 方向を規則化する (各サービス package が他サービスの client / gateway を import できる先を許可リスト化)。既存の量子別 CI (ADR-[[202606220716]]) に相乗りする。許可リストの初期値と lint 設定は実装 PR で確定する。
- **hard fail**: 違反はマージをブロックする。schema ロール強制 (ADR-[[202606231000]]) と同じ「弾く」思想で、warn 放置による形骸化を避ける。
- **範囲は triggered (CI) に限る**: 継続型の RED / SLO アラートは ADR-[[202606261100]] が既に担うため本 ADR に含めない。本 ADR は「CI で構造を弾く」枠を定める。
- **既存の暗黙 fitness を追認**: ADR-[[202606231000]] / ADR-[[202606210900]] / ADR-[[202606220716]] / ADR-[[202606261100]] を、名前のないフィットネス関数として本枠に位置づけ直す (参照のみ・再定義しない)。

## Consequences

- 設計原則が CI で機械的に守られ、無言の劣化を防ぐ。以降のフィットネス関数はこの枠に足していく。
- 許可リストの初期値決めが要る (現状の正当な同期呼び出し = order→payment / inventory / product 等を洗い出して許可、それ以外を禁止)。棚卸しは実装 PR。
- 過度に厳しいと正当な追加まで摩擦になる。許可リストの更新手順 (PR で明示追加) を運用に含める。
- `depguard` は import 単位のため「HTTP を直叩き」等の抜け道は完全には塞げない。gateway 経由を規約にして import で捕まえる前提とし、別の抜け道が問題化したら別の fitness function を足す。

## Alternatives considered

- **warn のみ (段階的に hard 化)**: 導入摩擦は小さいが放置され形骸化する。schema ロールと同じく hard で弾く。
- **継続型 (SLO) も本 ADR に統合**: 全体像は 1 枚になるが ADR-[[202606261100]] と重複し決定が 2 系統混ざる。triggered に絞る。
- **専用アーキテクチャテストツール (go-arch-lint 等) を導入**: 表現力は高いが依存ツールが増える。既存の golangci-lint (depguard) で始め、足りなければ後で足す。
- **フィットネス関数を入れずレビュー規律に委ねる**: 原則が人手依存で劣化する。方向 ADR-[[202607011621]] の「機械で守る」に反する。
