# ADR-202607011621: サービスベースからマイクロサービスへ段階移行する (主駆動特性と移行原則)

- Status: Accepted
- Date: 2026-07-01
- Relates to: ADR-[[202606170900]] (出発点の service-based。本 ADR で target style を更新), ADR-[[202606240522]] (DB-per-domain), ADR-[[202606262000]] (inventory 独立量子), ADR-[[202606211200]] (event-driven shipment), ADR-[[202606261212]] (Transactional Outbox。#96 で ADR-202606300600 へ移行中), ADR-[[202606261702]] (choreography 補償), ADR-[[202606261210]] (同期呼び出しの回復性), ADR-[[202606261216]] (致命/縮退分類), ADR-[[202606190900]] / ADR-[[202606301000]] / ADR-[[202606301100]] (横断データの現行 3 パターン)

## Context

- 出発点は service-based (ADR-[[202606170900]]): 粗粒度ドメインサービス + 当初は共有 DB。
- 実際の積み上げは既にその定義を越えている (推測でなく現状): DB はドメインごと 6 インスタンスへ分割済み (ADR-[[202606240522]])、inventory は独自 DB・独立量子として切り出し済み (ADR-[[202606262000]])、前進フローに非同期イベントが入り始め (ADR-[[202606211200]] / Outbox)、回復性・可観測性へ投資済み。共有 DB という service-based の身上から外れ、量子が増えている。
- しかし **target style が未宣言**。個々の ADR が「どの上位意図に奉仕するか」の背骨を欠き、量子粒度・同期/非同期・横断データの持ち方が都度別解になる (横断データが snapshot ADR-[[202606190900]] / pull ADR-[[202606301000]] / value ADR-[[202606301100]] の 3 パターン併存なのが実例)。
- checkout (`server/order/internal/handler/order_write.go`) は inventory→payment を同期 HTTP で束ねる暗黙のオーケストレーションで、payment 障害が checkout を同期的に落とす。**量子の可用性が独立していない**＝マイクロサービスの看板と現状の乖離。

## Decision

サービスベースから **マイクロサービスへ段階移行する**ことを表明し、主駆動特性と移行原則を定める。本 ADR は方向宣言に留め、個別方式 (横断データの既定・サーガ・order 状態機械) は後続 ADR へ切る (1 ADR=1 決定)。

- **主駆動特性を「信頼性 / 運用性 / 独立デプロイ性」に置く**。これまでの投資 (Outbox・冪等・縮退 ADR-[[202606261216]]・回復性 ADR-[[202606261210]]・可観測性) と一直線で、ローカル完結・費用ゼロの題材で計測できる特性に絞る。スケーラビリティ・性能は本題材では効果を計測しづらいため主駆動にしない。
- **結合の弱い縁から漸進する** (ADR-[[202606240522]] の分割方針を style 全体へ拡張)。1 PR 1 変更、hybrid の途中状態を許容する。
- **量子の独立を最優先で守る**。量子をまたぐ同期呼び出しを増やさない。前進フローの新規結合は非同期イベント (既存の Redis Streams + Outbox 経路) を既定とし、同期 HTTP は強整合が要る箇所に限る。
- **各サービスは自データを所有し、他ドメインの必要分は自前で持つ** (横断 JOIN 禁止は不変)。持ち方の既定は後続 ADR で確定する。
- **特性はフィットネス関数で守る**。schema 所有権を DB ロールで強制する ADR-[[202606231000]] と同じ発想で、「量子越えの同期呼び出しを勝手に増やさない」等を機械化していく。

## Consequences

- 背骨ができ、以降の ADR は「主駆動特性への奉仕」で採否を説明できる。個別判断が上位意図に紐づく。
- 移行中は hybrid 状態 (同期と非同期の混在、横断データ 3 パターン併存) が続く。これは既知の過渡で、後続 ADR で前進フローを非同期へ寄せ、横断データを 1 原則へ収斂させる。
- 分散トランザクション・結果整合・可観測性依存が増える (マイクロサービス税)。主駆動特性がこれを正当化する前提で、割に合わない局所は service-based 的な素直さを残してよい。
- 直近の具体化はいずれも別 ADR + issue に切る: (1) order を状態機械 + 遷移履歴へ (#96 が先送りした status モデリングの回収)、(2) checkout をオーケストレーション型サーガへ (前進フローの非同期化)、(3) 横断参照をローカル read model へ寄せる。

## Alternatives considered

- **service-based に留まる**: DB を共有へ戻し量子を粗粒度に保つ。ADR-[[202606240522]] / ADR-[[202606262000]] で既に割った現状と逆行し投資を捨てる。分散の難所を体験する学習目的にも合わない。
- **一気にマイクロサービス化 (ビッグバン)**: 全サービスを同時に非同期・独立化。レビュー不能で、弱い縁から手順を確立する学習効果を失う (ADR-[[202606240522]] と同じ理由で却下)。
- **イベント駆動アーキテクチャを target style にする**: 全面 choreography。跨ぐワークフローが増えると可視性・デバッグ性が落ちる (補償が既に choreography の ADR-[[202606261702]] にその兆し)。決済確定の即応など同期整合が要る箇所とも噛み合わない。マイクロサービスを軸に、必要な箇所へイベント駆動を差す。
