# ADR-202606211520: テストのケース分類で 4xx を準正常系・5xx を異常系に分ける

- Status: Accepted
- Date: 2026-06-21
- Relates to: ADR-[[202606180901]] (API エラーモデル) / ADR-[[202606180902]] (repository 実 DB 結合テスト) / [[test.md]] / [[go-test.md]]

## Context

- [[test.md]] の当初の `異常系` には 404 やバリデーション失敗 (400) が混ざり、stub 注入のテストでも
  400 / 401 / 404 / 409 / 422 と 500 / 502 が同じグループに並んでいた。
- 4xx は「入力や状態が不正」というクライアント起因の**想定済みの結果**、5xx はサーバが壊れて落ちる
  **想定外**で、性質が違う。同居させると「想定済みの 4xx を弾けているか」と「サーバ障害時の
  フォールバックが妥当か」という別々のレビュー観点が混ざり、網羅の薄さに気づけない。
- 認証 PR (#18) のレビューで論点になり、issue #28 として切り出した。

## Decision

**4xx は準正常系、サーバ起因の想定外 (DB エラー / 5xx) は異常系に置く。**

- 判定の軸は HTTP ステータスではなく**誰起因の失敗か**。ステータスは目印にすぎず、AppError で明示的に
  宣言した 502 のような「想定済みのサーバ応答」は準正常系に置いてよい。
- rdb の `ErrNotFound` / `ErrConflict` や gateway の上流 404 も、最終的に 4xx へ写るので準正常系。
- 既存テストの `name` ラベルも一括で揃える ([[test.md]] は「新規・改修のタイミングで揃える」だが、
  本 issue では一括適用)。

## Consequences

- レビュー時に 2 つの観点が別グループに分かれ、それぞれの網羅の薄さに気づける。
- ADR-[[202606180902]] の `異常系` は「実 DB で再現しづらい経路を stub で注入する」という**検証手段の軸**で、
  本 ADR の**ケース分類の軸**とは別物。当該 ADR は手段の記述として有効なまま残し、Status 行に部分更新を
  注記した。ケース分類の単一情報源は [[test.md]] + 本 ADR。
- 以後の新規・改修も同じ基準で分類すればよく、段階移行でも破綻しない。

## Alternatives considered

- **HTTP ステータスだけで機械的に振り分ける** — 単純だが、意図して宣言した 502 まで異常系へ落ちる。
- **分類を変えず `異常系` のままにする** — 観点が混ざる元の問題が残る。[[test.md]] の例示だけ直しても
  既存テスト名と乖離する。
- **ADR-[[202606180902]] の本文を書き換えて旧表現を消す** — ADR は結論を消さない方針 ([[adr.md]])。
  軸が別物なので上書きではなく併存させる。
