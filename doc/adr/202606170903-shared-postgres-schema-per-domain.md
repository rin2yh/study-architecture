# ADR-202606170903: 共有 Postgres + ドメインごとの schema 分離

- Status: Accepted (「単一インスタンス」前提は ADR-[[202606170909]]、migration の「中央集約」前提は ADR-[[202606180900]] でそれぞれ更新。schema 分離方針自体は維持)
- Date: 2026-06-17

## Context

Step 0 は共有 DB から始める（ADR-[[202606170900]]）。一方で将来のデータ所有権確定・DB 分割に備え、
最初からドメイン境界を可視化しておきたい。マイグレーションと sqlc のスキーマ入力を二重管理したくない。

## Decision

**共有 Postgres 1 つ**を、ドメインごとの **schema** で区画する。

- schema はドメイン名（`order` は SQL 予約語のため、識別子としては常に二重引用符を用いる）。
- マイグレーションは**中央集約**で goose の連番ファイル。goose のバージョンテーブルは 1 ディレクトリ 1 つが
  前提のため、ディレクトリは分けず schema 修飾でドメインを分離する。
- sqlc の schema 入力に goose のマイグレーションをそのまま与え、**スキーマの単一情報源**にする。
  各サービスは `omit_unused_structs` で自分の query が触れる型だけを生成する。
- ファイル名は辞書順 = 数値順になるよう**ゼロ埋め必須**（sqlc は辞書順でパースするため）。

## Consequences

- マイグレーション（goose）と型生成（sqlc）でスキーマの単一情報源を共有できる。
- 各サービスの生成コードは自分のテーブルにスコープされる。
- 以降は「他ドメインへの書き込みは持ち主サービス経由」に寄せ、結合の弱い縁から DB（やがて
  マイグレーションディレクトリ）を分割していく。
- 横断データ（注文時の商品価格・名称など）の持ち方は DB 分割時の論点として残す（ADR-[[202606190900]]）。

## Alternatives considered

- **schema を分けず public に同居**: ドメイン境界が見えず、将来の分割が困難。
- **最初からドメインごとに DB を分割**: Step 0 の「素直に立ち上げる」方針に反する。
- **マイグレーションをサービスごとにディレクトリ分割**: goose のバージョンテーブルがディレクトリ単位のため
  適用順序・横断管理が複雑。DB 分割時に移行する。
